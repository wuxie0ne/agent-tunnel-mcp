# agent-tunnel：Go 重做的产品需求草案

状态：待确认的需求草案（2026-09-28）。本文件描述**要解决的问题、用户可见行为和验收标准**，不是现有 Rust 代码的迁移清单，也不规定网络拓扑、协议、密码套件、Go 包、目录结构或部署方式。除“使用 Go 实现”外，不预设技术方案；标为待确认的内容不应被视为已批准的需求。

## 1. 目标与使用范围

让本地终端中的操作者或其 Agent，临时访问自己有权限管理的远端测试环境，执行命令、获取结果并在必要时交互；远端环境不必为此开放新的入站管理端口。访问应能被明确授予、限时使用和及时停止。软件计划从零使用 Go 实现，而非在现有实现上增量移植。

目标用户包括：发起任务的本地操作者、在操作者授权范围内使用工具的终端 Agent，以及在目标环境部署访问端的管理员。首要场景是**可丢弃的测试环境**；任何扩大到生产环境的诉求需要另行评估、验收和授权。

成功的最低标准：操作者能建立一次临时访问、确认目标、提交经授权的命令、读到对应输出和最终状态，并能主动终止访问；断线和超时不得被误报为执行成功，也不得悄悄重复执行可能产生副作用的命令。

## 2. 优先级

- **P0（首版必需）**：临时访问及失效、目标确认、命令执行与结果查询、安全授权、失联时的不确定结果处理、基本诊断和自动化验收。
- **P1（首版后按需推进）**：长任务管理、流式输出、交互式输入及终端、Agent 工具集成、运维可观测性增强。
- **待决策**：具体接入形态、交互能力是否进入首版、支持平台及多用户模型。优先级是建议，不代表用户已经确认范围。

## 3. 用户需求与验收口径

### R1. 建立并确认临时访问（P0）

操作者可以为指定目标创建或取得一次有明确有效期的访问，并在执行前辨认当前连接对应的目标。远端环境应能主动建立所需的对外连接，不以对公网开放目标入站管理端口为前提。访问到期、被撤销或主动关闭后，新操作必须被拒绝；失联后重连是否成功必须明确反馈，而不是默默切换到另一台机器。

**验收**：从无目标入站开放的测试环境完成一次连接、查询目标身份、执行和关闭；用错误、过期、已撤销的访问凭据分别尝试操作，均不能获得访问。目标变化时操作者可见并阻止旧任务误投递。

### R2. 受控执行命令（P0）

已获授权的操作者可指定命令及参数，取得任务标识、输出、退出状态和失败原因。需要能设置合理的执行期限，控制并发和资源消耗。命令运行时使用什么身份、具备哪些权限，必须事前可见；“限制在某个目录执行”不得被宣传为权限隔离。

**验收**：覆盖成功、非零退出、启动失败、超时和输出过大等情形；每个结果都能关联原始任务，输出截断可辨识；未授权请求不能触发远端副作用。

### R3. 授权与风险确认（P0）

远端执行默认不是无条件开放的能力。操作者应能区分“只是查看状态”与“可能改变目标状态”的操作；对后者必须提供明确的授权途径，并在无人能有效批准时安全拒绝。由远端命令输出、网页内容或 Agent 生成的文本，不得自动视作操作者批准。凭据应按最小必要范围分发；目标、会话和操作者的权限边界须可解释。

**验收**：无授权、有授权、授权过期及尝试以远端文本伪造批准均有可预期结果；审计记录足以回答谁请求了什么、何时授权或拒绝、实际触发了哪项操作，同时不泄露凭据或敏感输出。

### R4. 任务生命周期及不确定结果（P0）

操作者能查询任务的提交、运行、完成、失败等状态，并能请求停止仍在运行的任务。对于已经发送但确认丢失的命令，系统必须明确标示“可能已执行、结果未知”；不得为求便利使用新任务自动重试有副作用的命令。取消/超时后的清理和可能遗留的进程须可识别，不应把“发出停止请求”直接等同于“进程已终止”。

**验收**：在提交前、提交后、运行中和结果返回前人为中断连接，分别核对用户可见状态和实际执行次数；无法确认时呈现不确定状态，不声称恰好执行一次。重连后只恢复能被安全确认的状态。

### R5. 保护通信及敏感信息（P0）

未经授权的第三方不能读取或篡改命令正文、输入和输出；操作者须能确认通信对象与目标身份。凭据不得进入普通日志或公开的命令参数、错误信息、Agent 上下文。泄露、撤销与轮换的处置应有明确流程。对中间转发方能够观察的元数据和可用性风险，不得作出超出实际保护范围的承诺。

**验收**：模拟错凭据、身份不符、篡改、重放、凭据撤销和中间节点中断；未授权请求被拒绝，执行结果不被伪造为成功，敏感值不会出现在默认日志里。这里要求验证安全属性，不预先指定实现算法。

### R6. 错误、诊断与运维（P0）

提供本地可理解的连接、鉴权、授权、执行、超时、目标离线等错误分类和排查线索；支持正常启动、主动停止和清理临时访问。默认行为应适合测试环境的最小暴露原则，使用手册要清楚列出信任假设、已知风险和非生产边界。

**验收**：在无网络、目标离线、访问过期、无权限和执行失败时，操作者能区分故障位置及是否需要人工核对远端副作用；停止服务后不残留仍被认为有效的访问。

### R7. 长任务与交互（P1）

如需运行长任务，应允许查看增量输出及最终结果，并定义输出保留/清理规则。如需交互，应支持输入和终端尺寸变化，区分普通输入与交互终端；断开连接时应有清楚的终止或重连策略。该能力会增加远端输入风险，必须单独验收授权和清理。

**验收**：演示长任务输出、取消、断线及重新查询；交互能力一旦纳入范围，再覆盖输入、终端大小变化、断线和终止后的进程状态。首版未纳入时文档明确写为“不支持”。

### R8. Agent 集成（P1）

如产品面向终端 Agent，应提供易发现的远端状态、执行、结果查询和停止能力，且让操作者知道何时发生远端副作用。工具返回值与远端输出均是不可信数据，不得借工具集成绕过 R3 的授权。

**验收**：在选定的 Agent 客户端中完成一次请求、授权、结果查询和取消；伪造远端输出不能触发额外授权或获取本地秘密。具体集成接口在产品决策后确定。

## 4. 明确不承诺的能力

- 不把远端命令执行等同于沙箱隔离、最小权限或生产级访问控制；实际权限取决于运行身份和目标环境。
- 不承诺断网、崩溃、目标重启后的无损恢复或跨故障的恰好执行一次。
- 不将文件传输、端口转发、多人共享会话、无人值守批量调度及生产环境接入自动纳入首版。
- 不因为改用 Go 就宣称上述安全和可靠性问题已解决。

## 5. 进入开发前需确认的问题

1. 首版仅面向 Linux，还是包含 macOS/Windows？远端与本地的支持范围可以不同。
2. 首版的访问形式：只支持本地 CLI，还是同时提供 Agent 工具？哪些 Agent 客户端优先？
3. 授权应逐次确认、按时间窗授予，还是按命令/目标设置策略？哪些操作允许无人值守？谁有权撤销？
4. 命令执行是否必须具备交互终端、stdin、长任务断线后查询？是否需要限制允许执行的命令范围？
5. 目标可能同时有几位操作者、几个访问端？是否要求共享、排队或隔离？
6. 目标不可用时，是否允许部署额外转发服务或依赖现有基础设施？谁负责运营和审计？
7. 有效期、任务超时、输出大小、日志保留和访问回收应采用什么可配置的产品默认值？
8. 哪些平台和部署情形需要作为发布验收环境？是否计划支持生产环境（若是，需要另立安全要求）？

## 6. 建议的需求验收顺序

先确定第 5 节中的首版边界与威胁模型，再验证 R1、R3、R5 的访问与安全属性，然后完成 R2、R4、R6 的执行和故障语义；只有在这些验收通过后再纳入 R7、R8。测试应同时包括正常路径、错误路径、失联/过期竞态和未授权请求。任何实现阶段的测试通过都只能证明对应测试范围，不能替代生产安全审计。
